# FinCore: Ledger-Based Banking API

A secure, scalable, and audit-ready banking transaction backend engine. This system enforces absolute data integrity using a ledger-based "single source of truth" architecture, handling concurrency, race conditions, and financial compliance at the database level.

---

## ⚡ Quick Start (Short Version)

### Core Features
*   **Immutable Ledger Architecture:** Every transaction is an append-only log; balances are derived dynamically via MongoDB aggregation.
*   **ACID Compliance:** Multi-document database transactions handle concurrent debit/credit workflows safely.
*   **Idempotency Layer:** Prevents double-charging or duplicate transactions caused by network retries.
*   **Enterprise Security:** Token-blacklisted JWT sessions, bcrypt hashing, and secure cookie storage.

### Tech Stack
*   **Backend:** Node.js, Express.js
*   **Database:** MongoDB (Mongoose ODM)
*   **Security & Utils:** JWT, Bcrypt, Nodemailer + Google OAuth2

### Fast Local Setup
1.  **Clone & Install:** `git clone <repo-url> && npm install`
2.  **Env Setup:** Create a `.env` file with `PORT`, `MONGO_URI`, `JWT_SECRET`, and `SMTP_OAUTH` details.
3.  **Run:** `npm start` (Runs on `http://localhost:5000`)

## 🛠️ Detailed Documentation

### 🏛️ System Architecture & Data Integrity
FinCore moves away from unreliable "flat balance tracking" fields. Instead, it utilizes a strict, financial-grade **double-entry ledger system**.

*   **Single Source of Truth:** Account balances are not stored as a static number that gets incremented/decremented. Instead, they are computed dynamically through MongoDB database aggregation pipelines summarizing the historic append-only ledger entries.
*   **Race Condition Mitigation:** Uses MongoDB Sessions (`session.startTransaction()`) to execute atomicity. If a debit succeeds but a credit fails, the entire operation rolls back instantly.
*   **Idempotency Layer:** Every transaction payload requires a unique `idempotency-key` generated by the client. The backend caches processing keys; duplicate requests return the cached response instead of processing the transaction again.

### 🗄️ Database Optimization & Schema Strategy
To handle high-throughput read/write operations, the database schema implements optimized compound indexing.

*   `{ accountId: 1, createdAt: -1 }` ensures near-zero latency when running aggregation pipelines to calculate balances or fetching account history statement logs.
*   `{ idempotencyKey: 1 }` enables $O(1)$ lookups to drop duplicate API requests safely at the gateway level.

### 🔐 Security & Access Control
*   **Session Management:** Implements JWT access tokens distributed via secure, HTTP-only, SameSite cookies to protect against Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF).
*   **Token Blacklisting:** Includes a Redis/database backed blacklisting mechanism on logout middleware to invalidate active tokens immediately.
*   **Account States:** Middleware automatically intercept incoming transactions to validate account flags (`Active`, `Frozen`, `Closed`).

## 🚦 API Endpoints Map

### 👤 Authentication
*   `POST /api/v1/auth/register` - Create user profile + trigger welcome email
*   `POST /api/v1/auth/login` - Authenticate user & issue HTTP-only cookie session
*   `POST /api/v1/auth/logout` - Blacklist current session token

### 🏦 Account Management
*   `POST /api/v1/accounts` - Provision a new bank account
*   `GET /api/v1/accounts/:id/balance` - Compute balance via aggregation pipeline
*   `PATCH /api/v1/accounts/:id/status` - Freeze/Close account (Admin restricted)

### 💸 Financial Transactions
*   `POST /api/v1/transactions/transfer` - Execute ledger-based debit/credit transfer
*   `GET /api/v1/transactions/history` - Fetch scannable, paginated audit statements
